# C5: exam_resilience (5.3 Failure-Resilient Examinations): server AND browser engine
This is the headline innovation. Judges will pull the network cable, refresh, close the laptop and switch devices. It must survive all of that without giving anyone extra time.

## Backend: `backend/crates/exam_resilience`
Depends on exam_attempts (C4, building in parallel) for `store::upsert_answer` and `finalize`. Use the signatures in HANDOFF section 4. If they don't exist yet when you compile, write against them anyway, note it, and re-check later.

**`POST /attempts/{id}/heartbeat`** (`HeartbeatInput`):
- Owner only; the attempt row is locked.
- Insert into `attempt_heartbeats` (online and pending) and update `last_heartbeat_at`.
- If the previous heartbeat is older than 45 s, record an `offline`/`online` event pair with the gap (a server-verified outage).
- Return `HeartbeatResult` with:
  - a fresh lease from `examcore::issue_lease`
  - serverNow, deadlineAt, status
  - deviceActive (`X-Attempt-Device` == active_device)
  - announcements newer than `lastAnnouncementAt`
- Rate limit at 20/min per attempt. Lazy finalize if past deadline + grace.

**`POST /attempts/{id}/journal {entries: JournalEntry[]}`** (max 200 entries, in seq order):
- Lock the attempt row. Then, for each entry:
  - verify the lease: `examcore::verify_lease` (else reason `lease`)
  - `writtenAt == lease.issuedAt + elapsedMs`
  - `elapsedMs >= 0`
  - `writtenAt <= receivedAt(now)` (else `future`)
  - `writtenAt <= deadline_at` (else `late`)
  - the item belongs to the attempt; validate the response as in C4 (C4 exposes a validator; if not, re-implement the same rules)
  - the hash chain: `hash == examcore::chain_next(prev, seq, itemId, response, writtenAt)`, where prev is the server's `journal_head`, or `journal_genesis` when head is null, and seq is `journal_seq + 1` (else `chain`; a broken chain rejects that entry and everything after it)
- Valid entries go to `upsert_answer` with source `journal`, written_at from the lease, and client_seq = the entry seq + 1_000_000_000. Journal seqs sit in a separate high range so they always win over older online saves. Document why: the journal entry is newer than any online save. Then advance `journal_head` and `journal_seq`.
- Closed attempts: entries are accepted only while now <= deadline + `JOURNAL_GRACE_SECS` (from exam_attempts). After that, reason `closed`.
- Record one `journal_synced` event with the counts (notice severity if any were rejected), then re-run autograde if the attempt is already finalized.
- Return `JournalSyncResult`.
- Document the threat model in a doc comment, including the residual risk: a candidate offline inside the window could consult resources while offline, but that's the same risk as being online. They can't extend time, because claimed times are bounded by the lease, by real elapsed time and by the deadline.

**`POST /attempts/{id}/takeover`**:
- Device failure recovery: the owner on a new device sets `active_device` to the header value and `device_changed_at`, and records the event `device_takeover` (warning severity, with the old and new device hashed and short).
- The old device's next save gets 409 reason `device`.
- Rate limit at 5/hour per attempt.

**`GET /attempts/{id}/outages`** (exam owner): compute verified outages from heartbeat gaps of 45 s or more within [started_at, min(deadline, submitted_at)]. Mark one credited if a time_credit overlaps it.

**`POST /attempts/{id}/time-credit {seconds, reason, outageFrom?, outageTo?}`** (exam owner or admin):
- The attempt must be in_progress, or expired within the last 30 min (re-open: set status back to in_progress and finalized_by null).
- seconds must be <= the total uncredited verified outage seconds + 60, unless the viewer is an admin. Reason 3-500 chars.
- Insert into time_credits and extend deadline_at by the seconds, but never beyond `ends_at + 60 minutes`.
- Audit `exam.time_credit` and record the event `time_credit`. Return the new deadline.
- Tests: forged lease, tampered chain, late entry, future entry, credit cap, takeover blocks old device.

## Web engine: `web/src/lib/exam/`
H2's workspace UI consumes this. Make the hook API exactly as below and document it at the top of `use-attempt.ts`.
- `clock.ts`: server clock offset. Track `serverNow - performance.now()`-based offset from every response, and expose `serverNowMs()`. Never use `Date.now()` for deadlines.
- `device.ts`: stable device id in localStorage (`invigil.device`, 24 random chars via crypto.getRandomValues). Sent as the `X-Attempt-Device` header on every attempt call.
- `journal.ts`: IndexedDB store `invigil-journal` (plain `indexedDB` API, no dependency):
  - one object store keyed by [attemptId, seq], plus a meta store for the head, seq and the latest lease (with `performance.now()` at receipt, and `Date.now()` as a fallback when the page reloads while offline: on reload `performance.now()` restarts, so persist `receivedAtWall` and use the wall-clock delta capped by the lease, documenting the trade-off)
  - `canonicalJson` matching Rust `examcore::canonical_json` (sorted keys, compact)
  - `chainNext` with `crypto.subtle.digest('SHA-256')`, byte-for-byte the same as `examcore::chain_next`: bytes = utf8("journal.v1") + prev bytes + utf8(String(seq)) + utf8(itemId) + utf8(canonical) + utf8(String(writtenAt))
  - base64url without padding
  - Add a vitest test file `journal.test.ts` with a fixed vector: compute it in Rust with a `#[test]` in your crate that prints the expected hash for a fixed genesis, and assert the same in TS.
- `sync.ts`: the save queue.
  - Online: PUT the answer immediately (debounce written answers by 800 ms), with retry and backoff on network errors (1s, 2s, 4s… max 15s).
  - Offline (navigator.onLine false, a fetch failure, or the heartbeat failing twice): append to the journal instead (when `journal.enabled`).
  - On reconnect: POST `/journal` in batches of up to 200, then drop acknowledged entries.
  - On a 409 `device` stop and surface `deviceActive=false`. On 409 `closed` surface `closed`.
  - Every save carries a monotonically increasing clientSeq per attempt, persisted in IndexedDB so a refresh never reuses a seq.
- `network.ts`: `useNetworkStatus()` returns `{online, quality: 'good'|'unstable'|'offline', lastOkAt, rttMs}`. Unstable means the last 3 heartbeats had RTT > 1500 ms or failures.
- `use-attempt.ts`: `useAttempt(attemptId)` returns
  `{ status: 'loading'|'ready'|'error', error, payload, answers: Record<itemId, {response, flagged, state: 'saved'|'saving'|'queued'|'offline'|'error'}>, setAnswer(itemId, response, typing?), toggleFlag(itemId), saveState: 'saved'|'saving'|'offline'|'syncing'|'error', pendingCount, remainingMs, deadlineAt, closed, deviceActive, takeover(), submit(): Promise<void>, announcements, network }`
  - Heartbeat every 15 s, every 5 s while offline-recovering.
  - `remainingMs` ticks every 250 ms from server-offset time.
  - At remainingMs <= 0 it stops accepting edits, flushes the journal and calls submit (the server finalizes anyway).
  - It restores answers from the payload and merges un-synced local journal entries on refresh.
- Run `pnpm typecheck` and `pnpm test`.
