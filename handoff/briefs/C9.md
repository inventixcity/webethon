# C9: integration, hardening, DevOps, docs, end-to-end test

1. **Server wiring** (`backend/crates/server/src/lib.rs`, `housekeeping.rs`):
   - Call `examcore::init_keys()` at startup.
   - Every 20 s in housekeeping, call `exam_attempts::sweep(&db)` (log the count when > 0; never crash the loop).
   - **Unmount** the routers this product doesn't use, to shrink the attack surface: payments, booking, places, social, teams, transfer, webhooks, shares, assist, analytics, flags, records (and realtime if nothing needs it). Keep auth, admin, files only if used (otherwise unmount), ai (optional grading suggestions), and all exam_* routers.
   - Keep the crates compiling; just don't mount them. If `finish_router` needs `storage` or `hub` args, keep them.
   - `bash scripts/cargo.sh check -p server` must pass. Other workers' crates may be mid-edit; if they fail to compile, wait and retry. Don't edit them.
   - Add the production startup checks to the API: `EXAM_LEASE_KEY` (32+ chars) and `RESULT_SIGNING_KEY` (valid base64 of 32 bytes) are required when APP_ENV=production. Refuse to start with a clear message. Do this in server main/lib, not in kernel.
2. **Web hardening** (`web/next.config.ts`, `web/src/proxy.ts`):
   - A strict CSP with nonces if feasible, otherwise `default-src 'self'; script-src 'self' 'unsafe-inline'` only as needed by Next; `connect-src 'self'`; `img-src 'self' data: blob:`; `frame-ancestors 'none'`; `object-src 'none'`; `base-uri 'self'`; `form-action 'self'`.
   - Also HSTS, Referrer-Policy strict-origin-when-cross-origin, Permissions-Policy (camera=(), microphone=(), geolocation=()), X-Content-Type-Options, COOP same-origin.
   - Check what already exists first. Make sure `/verify/*` and `/invite/*` are public in the proxy, and `/app/*` and `/exam/*` require a session cookie.
   - Static assets get long immutable caching; API and pages get no-store.
3. **Deployment** (`deploy/azure/`). Everything by az CLI, scripted. The user's internet is slow, so build in the cloud.
   - `deploy/azure/deploy.sh`, idempotent:
     - Read `.env.production` at the repo root (gitignored; contains DATABASE_URL, PROXY_SECRET, CODE_PEPPER, EXAM_LEASE_KEY, RESULT_SIGNING_KEY, MFA_ENCRYPTION_KEY, SMTP_URL or RESEND_API_KEY, EMAIL_FROM, AI_*).
     - Create resource group `invigil-rg` (location `southeastasia`, configurable).
     - Register providers Microsoft.App and Microsoft.OperationalInsights. Create an ACR `invigilacr<suffix>` (Basic).
     - `az acr build --registry ... --image invigil-api:<git sha> backend/` (cloud build: only the source is uploaded).
     - Create a Container Apps environment and the container app `invigil-api`: ingress external, target port 8080, min 1 / max 3 replicas, 0.5 CPU / 1Gi.
     - Secrets via `--secrets` and env via `secretref:`. Health probes on the existing health endpoints (read the server for the paths).
     - Set APP_ENV=production, RUN_MIGRATIONS=true for the first deploy, APP_ORIGIN from an arg, TRUSTED_PROXY_HOPS=1.
     - Print the FQDN.
   - Make the backend Dockerfile build the release `api` binary with the new crates included (check the COPY lines include all crates and migrations), and copy `crates/exam_questions/seed` if it's include_str!'d (compile-time, so no copy is needed; verify).
   - `deploy/azure/seed.sh`: runs `api seed-demo` as a one-off via `az containerapp exec` or a job.
   - Vercel: `web/vercel.json` or `vercel.ts` if needed, and document `vercel env add API_ORIGIN / PROXY_SECRET / NEXT_PUBLIC_API_ENABLED`.
   - Don't run the deploy yourself. The lead runs it after az login. Validate the script with `bash -n`.
4. **CI** (`.github/workflows`): keep `backend.yml` (cargo check, test, clippy) and `web.yml` (typecheck, test, build), and update the paths: `ui components` is now `web`, and the crate names changed. Delete workflows for unused things (k8s, deploy-web) or adapt them. CodeQL can stay.
5. **Docs** (`README.md` at the root, `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/INNOVATION.md`; never mention any other project):
   - The README is concise: what Invigil is, features mapped to the requirements (3.1–3.8, 4.1–4.8, 5.1, 5.3), tech stack and why, setup (docker compose, cargo.sh, pnpm), env vars, test credentials (from the C8 seed: `admin@invigil.app` / `examiner@invigil.app` / `candidate@invigil.app`, password `Invigil#Demo2026`), deployment, and the innovation summary.
   - SECURITY.md is a threat model: STRIDE-style table, OWASP ASVS 5.0 mapping of the controls.
   - INNOVATION.md covers 5.3 and 5.1 design, trade-offs and residual risks (read HANDOFF and the C5/C7 briefs in `handoff/briefs/`).
   - Remove or replace leftover docs under `backend/` that describe unrelated features (`backend/openapi.yaml` can stay but must not describe unmounted routes; trim or delete it).
6. **E2E** (`tests/e2e/`): replace the old suites with `tests/e2e/exam-flow.mjs` (plain Node 24 fetch, no deps).
   - The flow: examiner signs in → creates 2 questions → creates an exam → assigns → publishes → enrolls a candidate (gets the invite link) → candidate accepts the invite → starts → saves answers → submits → examiner grades → publishes results → candidate sees the result → public verify succeeds.
   - Negative checks: a candidate can't read the examiner endpoints; a second start returns the same attempt; a save after submit is refused; tampering with the verify code is invalid.
   - API_URL env var. Document it in the README.
   - Delete `tests/browser` and `tests/load` unless they're trivially adaptable (prefer deleting).
